# Pharmacy Routine Portal — Daffodil International University

A modern, highly interactive **Class & Laboratory Routine Portal** for the **Department of Pharmacy, DIU**, covering **Batch 29 – Batch 38** (sections A/B, laboratory groups A1 · A2 · B1 · B2) and fully scalable to future batches, semesters, rooms, faculty and lab groups — without any code changes.

> **The core principle: routines are completely dynamic and batch-specific.** No batch is assumed to share days, off days or structure with another. Selecting *Semester → Batch → Section → Lab Group* instantly generates the personalized timetable.

| **Search Routine** | Search everything by faculty name/initials, course name/code, room number, batch — results open the detail modal |
| **Announcements** | Notices, urgent alerts, events, routine updates — filtered by category & batch, pinned items on top |

### Export
PDF (jsPDF — university name, department, semester, batch, section, lab group, generation date + complete grid + legend), **PNG image** (html2canvas) and **Print** (print-optimized layout with the same header).

### Conflict prevention (before save)
1. Faculty double-booking — same faculty, same day + slot
2. Room double-booking — same room, same day + slot
3. Section overlap — a section can never have two classes at once
4. Lab-group overlap — A1/A2/B1/B2 can never overlap their own sessions

The admin form live-checks all four rules and shows exactly what conflicts ("`DSR is already teaching Pharmacology (Batch 34 Section A) in AB-403 on Saturday (8:30 – 10:00)`"). The same rules are also enforced **server-side** by a PostgreSQL trigger (`supabase/schema.sql`), plus a `check_routine_conflict()` RPC.

### Off-day management (batch-specific)
Off days live in `batch_off_days` keyed by **Semester + Batch + Day** — independent per batch. Examples built into the seed:

- Batch 29 → off **Tuesday**; Batch 30 → off **Thursday**
- Batch 32 → off **Saturday + Wednesday**; Batch 37 → off **Saturday + Sunday**
- Batch 34 → classes on Saturday, off **Saturday**? — no: Batch 34 classes on **Sunday–Thursday**, off **Saturday**

Every batch's active days and off days are computed from the database, never hard-coded.

## 🧱 Tech stack

- **React 18 + TypeScript + Vite** — single-page app, reusable components (`Timetable`, `ClassCard`, `SelectionPanel`, `Modal`, `Segmented`, `Toggle`, `Legend`, `CrudTable`…)
- **Tailwind CSS** — responsive design, dark mode (class strategy), print stylesheets
- **Zustand** — theme, branding/colors, auth session, routine selection (persisted)
- **Supabase PostgreSQL** — 13 relational tables, RLS, conflict trigger, RPC
- **Embedded demo database** (`src/lib/seed.json`, generated by `scripts/generate-seed.mjs`) — the app is 100% functional with zero backend: same data-access API, same shapes

```
src/
├── lib/         types, db (supabase|demo), conflicts, routine (dynamic builder),
│                exports (pdf/png/print), store, ui kit, data provider
├── components/  Layout, ClassCard + modal, Timetable (grid/daily/mobile), SelectionPanel
├── pages/       Home, Routine, FacultyRoutine, RoomSchedule, LabRoutine, Search, Announcements, Login
├── admin/       Dashboard, RoutineEntries(+live conflict check), OffDays, Catalog, Settings…
└── App.tsx      routes (public + /admin/**, guarded by role)
```

### Connect Supabase (production)

1. Create a Supabase project; run **`supabase/schema.sql`** in the SQL Editor (tables, constraints, **conflict trigger**, RLS policies, auto profile trigger).
2. Seed catalog data — the SQL file documents the shape; `scripts/generate-seed.mjs` produces a deterministic dataset you can replay (`node scripts/generate-seed.mjs` → `src/lib/seed.json` is also the demo source).
3. Copy `.env.example` → `.env` and set `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`.
4. Create users in **Authentication → Users**; promote the first one with `update profiles set role='admin' where id='<uuid>';`

With Supabase connected, RLS keeps catalog + routine data readable by everyone (students need no account), while **writes are admin-only** (faculty may update their own entries).

## 🗄️ Data model (13 tables)

`semesters` · `batches` · `sections` *(`batch_id`)* · `lab_groups` *(`section_id`)* · `faculty` *(type: regular/guest/ged/nfe/external)* · `courses` *(department: pharmacy/ged/nfe/agriculture → color coding)* · `rooms` *(theory/lab)* · `time_slots` *(6 × 1h30m)* · `class_days` · **`routine_entries`** *(semester+batch+section+optional lab_group+course+faculty+room+day+slot+type+status+notes)* · **`batch_off_days`** *(semester+batch+day — separate table so the academic calendar evolves independently)* · `announcements` · `settings` *(branding + color scheme)* · `profiles` *(auth ↔ role)*

**Theory classes → `lab_group_id NULL`; laboratory classes → always a specific group (A1/A2/B1/B2).** Check constraints + a trigger enforce this in the database itself.

## 📈 Scalability

Adding **Batch 39** (admin → Batches) auto-creates Sections A/B and groups A1/A2/B1/B2; add its courses, routine entries and off-day calendar — interface picks everything up. Same for new semesters, rooms, faculty, days and time slots.
